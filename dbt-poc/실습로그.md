## STEP 2 · ref() 치환 확인
- `{{ ref('stg_customers') }}` → 컴파일본에서 무엇으로 치환?:
  - 원본 `models/customers.sql`: `select * from {{ ref('stg_customers') }}`
  - 컴파일본 `target/compiled/.../customers.sql`: `select * from "jaffle_shop"."main"."stg_customers"`
  - → **ref()가 `"<database>"."<schema>"."<model>"` 완전수식 식별자로 치환**됨을 직접 대조 확인. (database=jaffle_shop, schema=main)
- `show tables` 결과: `customers, orders, raw_customers, raw_orders, raw_payments, stg_customers, stg_orders, stg_payments` (8개)
  - raw_*(seed=실테이블) / stg_*(view) / customers·orders(table) 가 한 DuckDB 파일에 공존.
- 메모: `select * from customers limit 5` → customer_id·이름·first_order·most_recent_order·number_of_orders·customer_lifetime_value 컬럼. stg_orders+stg_payments를 고객 단위로 집계한 마트임이 데이터로 확인됨.

## 이론 노트 정오표 (dbt 이론.md와 다르거나 새로 안 것)
- **`ref()` 치환 형태**: 막연히 "테이블명으로 바뀐다"가 아니라 `"db"."schema"."name"` 3단 완전수식으로 치환됨(DuckDB 어댑터 기준). compiled SQL을 직접 열어봐야 체감됨.
- **materialization 차이가 객체 종류로 드러남**: jaffle 기본 설정상 stg_*는 **view**, customers/orders는 **table** 로 생성됨(`show tables`엔 view도 함께 보임). 같은 SQL이라도 materialization에 따라 물리 객체가 달라짐을 확인.
- **build 위상정렬**: `dbt build`는 seed/model/test를 한 DAG로 묶어 의존 순서대로 실행. 상위 실패 시 하위 SKIP(이번엔 전부 PASS라 SKIP 미발생 — SKIP 재현은 품질·이력 주차 과제).
- **Python 3.9 → dbt 1.10 고정**: 계획서엔 없던 환경 제약. 최신 1.11 매끄러운 진행 원하면 Python 3.11+ 권장(현재는 `--no-version-check`로 우회 중).
