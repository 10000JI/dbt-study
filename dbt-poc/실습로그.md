## STEP 5 · source()로 적재 (jaffle 미검증분)

## STEP 6 · staging→intermediate→marts (3계층, jaffle엔 intermediate 없었음)
- **staging(view) 5종**: stg_orders/order_items/products/payments/customers. 그레인 검증 n=k(키 유일).
- **intermediate(view) 1종**: `int_order_items_enriched` (order_item 그레인, n=k=112,650 → 조인 행 증식 없음).
- **marts(table) 4종**: `dim_customers`(99,441) · `dim_products`(32,951) · `fct_orders`(99,441, 주문 1행 그레인 n=k) · `fct_daily_sales`(634일).
- 전체 `dbt build`: **PASS=40 WARN=0 ERROR=0 SKIP=0** (1 seed·4 table·6 view·29 test, 6.78s). 실데이터인데도 테스트 전부 통과(고아키/미등록값 0).

## STEP 7 · 테스트 (generic + singular + SKIP 게이트)
- **generic**: unique/not_null(PK), relationships(order_items·payments → orders, fct_orders → dim_customers), accepted_values(order_status 8값·payment_type 5값) — `arguments:` 신문법.
- **singular**: `assert_fct_orders_amounts_non_negative`(금액 음수 0행 → PASS) + 복합키 유일성 3종(order_items·payments·int, order_id+seq → PASS) + `assert_fct_orders_delivered_has_payment`(**severity=warn**).
  - ⚠️ **데이터 품질 발견**: delivered인데 아이템 있고 결제 0인 주문이 **1건** 존재(Olist 알려진 결제 누락 quirk). warn으로 두어 빌드는 그린(`PASS=45 WARN=1 ERROR=0`) 유지하면서 이슈를 노출 → **singular 테스트가 실데이터 결함을 잡는 사례** 체득.
- **상위 실패→하위 SKIP 게이트 재현(jaffle 미검증분)**: `_staging.yml`에서 order_status accepted_values의 `'delivered'`를 임시 제거 → `dbt build -s stg_orders+`:
  ```
  FAIL accepted_values_stg_orders_order_status (Got 1 result)
  SKIP fct_orders / fct_daily_sales (+ 그 테스트들)
  Done. PASS=7 WARN=0 ERROR=1 SKIP=9
  ```
  → 상위 테스트 실패가 게이트가 되어 하위가 SKIP됨을 실제로 관찰. 복구 후 PASS=40 재확인.

## STEP 8 · snapshots SCD2 (jaffle 미검증분)
- `snap_orders_src`(shipped 200건 mutable table) → `orders_snapshot`(strategy=check, check_cols=[order_status]).
- 1차 snapshot: 200행 모두 현재행(dbt_valid_to NULL).
- 한 주문(`002f19a6...`) status를 `UPDATE shipped→delivered` → 2차 snapshot:
  | order_status | dbt_valid_from | dbt_valid_to |
  |---|---|---|
  | shipped | 09:21 | **09:22 (닫힘)** |
  | delivered | 09:22 | **NULL (현재행)** |
  - 총 201행/현재 200행 — 이력 1건 추가. 이론 5.4 SCD2(`dbt_valid_from/to`) 첫 실검증.

## 이론 노트 정오표 (dbt 이론.md와 다르거나 새로 안 것)
- **`ref()` 치환 형태**: 막연히 "테이블명으로 바뀐다"가 아니라 `"db"."schema"."name"` 3단 완전수식으로 치환됨(DuckDB 어댑터 기준). compiled SQL을 직접 열어봐야 체감됨.
- **materialization 차이가 객체 종류로 드러남**: jaffle 기본 설정상 stg_*는 **view**, customers/orders는 **table** 로 생성됨(`show tables`엔 view도 함께 보임). 같은 SQL이라도 materialization에 따라 물리 객체가 달라짐을 확인.
- **build 위상정렬**: `dbt build`는 seed/model/test를 한 DAG로 묶어 의존 순서대로 실행. 상위 실패 시 하위 SKIP(이번엔 전부 PASS라 SKIP 미발생 — SKIP 재현은 품질·이력 주차 과제).
- **Python 3.9 → dbt 1.10 고정**: 계획서엔 없던 환경 제약. 최신 1.11 매끄러운 진행 원하면 Python 3.11+ 권장(현재는 `--no-version-check`로 우회 중).
- **(Olist) external source의 `{name}` 치환**: dbt-duckdb는 `meta.external_location`에 함수호출(`read_csv_auto(...)`)을 쓰면 따옴표 없이 그대로 FROM에 렌더하고, `{name}`은 테이블명으로 치환. → seed 없이 raw CSV를 source()로 직접 참조 가능(우리가 만든 프로젝트는 `require-dbt-version`을 직접 지정해 **`--no-version-check` 불필요**).
- **(Olist) SKIP 게이트는 "상위 테스트 실패"가 트리거**: 모델 빌드 실패가 아니라 stg_orders의 *테스트* 실패가 하위 fct_*를 SKIP시킴. `int_order_items_enriched`는 stg_orders의 하위가 아니라(stg_order_items 의존) SKIP 대상이 아니었음 — DAG 의존을 정확히 봐야 SKIP 범위를 안다.
- **(Olist) snapshot check 전략**: `updated_at` 없이 `check_cols`로 컬럼 변화만 감지. 정적 CSV는 그냥은 SCD2가 안 보여 mutable 테이블을 만들어 직접 UPDATE해야 관찰됨.
