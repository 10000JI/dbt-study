1 dbt가 도대체 뭐야?

한 문장: "창고(데이터베이스) 안에 쌓인 raw 데이터를, SQL로 깔끔하게 가공해 쓸 수 있게 만들어주는 도구"

비유를 들어볼게요. 🏭

마트에 원재료(raw 데이터)가 잔뜩 들어왔어요 — 주문 기록, 고객 명단, 상품 목록, 결제 내역이 따로따로 흩어진 CSV 파일들입니다. 이대로는 "어제 매출이 얼마야?" 같은 질문에 답할 수 없어요. 가공이 필요합니다.

dbt는 이 가공 과정을 관리하는 주방 매니저예요. 요리(연산) 자체는 안 하지만 — 그건 데이터베이스(DuckDB·BigQuery 등)가 합니다 — "어떤 재료로 → 무슨 순서로 → 어떤 요리를 만들지" 레시피를 관리하고, 맛 검사(테스트)하고, 메뉴판(문서)을 자동으로 만들어줍니다.

핵심: 사용자는 SELECT 문(원하는 결과를 묘사하는 SQL)만 작성합니다. CREATE TABLE, 실행 순서, 의존성 관리 같은 귀찮은 건 전부 dbt가 알아서 해줍니다. → 이 방식을 "분석 엔지니어링"이라고 불러요.

2 그냥 데이터베이스에 SQL 치면 되잖아? 왜 dbt?

맞아요, SQL은 데이터베이스에 직접 쳐도 돌아갑니다. dbt가 주는 건 "속도"가 아니라 "신뢰와 관리"예요.

상황데이터베이스에 직접 SQLdbt로 관리
코드 보관여기저기 흩어짐, "그때 그 쿼리 뭐였지?".sql 파일 → Git 버전관리
실행 순서사람이 "A 먼저, B 나중" 외워야 함ref()로 순서 자동 결정
데이터 검증매번 눈으로 확인테스트로 자동 단언
문서/계보없음자동 생성 (이 노트의 그림들!)
한 줄 기준: "한 번 보고 버릴 쿼리는 데이터베이스에 직접, 계속 유지·반복·공유할 변환 로직은 dbt"

매출 집계 리포트

각 단계는 앞 단계의 결과를 입력으로 받습니다. dbt에서는 이 "앞 단계 가리키기"를 {{ ref('모델이름') }} 로 표현하는데, 이렇게만 쓰면 dbt가 알아서 "아, 이건 저것보다 먼저 만들어야겠네" 하고 순서를 정합니다.

-- 예: 매출 마트가 "정리된 주문"을 가져다 쓴다
select * from {{ ref('stg_orders') }}   ← "정리된 주문 모델을 먼저 만들고, 그 결과를 달라"
왜 4단계로 나눌까? 한 번에 거대한 SQL 하나로 만들 수도 있지만, 단계를 나누면 ① 각 단계를 따로 테스트·재사용할 수 있고 ② 문제가 생겼을 때 어디가 잘못됐는지 바로 찾을 수 있어요. (레고 블록처럼 조립)

4 4개 레이어 자세히 보기

색깔은 뒤 그림(계보)의 노드 색과 같습니다 — 한눈에 "어느 단계 것"인지 구분하려고요.

● Source / Seed

raw 원본

Olist CSV 6개. dbt가 만든 게 아니라 밖에서 들어온 데이터. source()로 가리킴.

orders·order_items·customers·products·payments + 카테고리 번역

● Staging (view)

청소 단계

raw 1개당 staging 1개(1:1). 컬럼명 통일, 타입 변환(문자→날짜/숫자)만. 합치지 않음.

stg_orders · stg_customers · stg_products · stg_order_items · stg_payments

● Intermediate (view)

조립 단계

여기서 처음으로 여러 개를 합침. 주문 아이템 + 상품 카테고리(영문)를 조인.

int_order_items_enriched

● Marts (table)

완성 리포트

실제로 사람이 보는 최종 결과. 비즈니스 질문에 답하는 표.

fct_orders · fct_daily_sales · dim_customers · dim_products

fct? dim? 이름 규칙

fct_(fact, 사실)는 "사건/숫자"를 담아요 — 주문이 일어났고, 금액이 얼마였다. dim_(dimension, 차원)은 "설명"을 담아요 — 이 고객은 누구고, 이 상품은 뭔지. 매출 분석은 보통 "fact(숫자)를 dim(설명)으로 쪼개 보는" 식이에요. (예: 상품 카테고리(dim)별 매출(fact))

view vs table? staging·intermediate는 view — 매번 새로 계산하는 "바로가기". marts는 table — 결과를 실제로 저장해 빠르게 조회. 똑같은 SELECT라도 설정에 따라 만들어지는 물건이 달라집니다. 이 설정은 폴더별로 dbt_project.yml에 한 번만 적어두면 됩니다.

5 계보(Lineage) — dbt가 자동으로 그려준 지도

dbt의 가장 멋진 기능: ref()로 연결만 해두면, 데이터가 어디서 와서 어디로 가는지 지도를 자동으로 그려줍니다. (dbt docs 명령 한 줄)

바로 이게 "dbt를 쓰면 좋은 이유"의 결정판이에요. 데이터베이스에 SQL만 쳤다면 이런 지도·문서는 존재하지 않습니다. 새 팀원이 와도 이 그림 한 장이면 전체 구조를 파악하죠.

6 데이터 테스트 — "이 데이터 믿어도 돼?"

코드에 버그가 있듯 데이터에도 문제가 생깁니다. dbt는 데이터에 대한 규칙을 걸고 매번 자동 검사해요.

일반(generic) 테스트

YAML에 한 줄로 거는 재사용 규칙 4종:

  • unique — 주문 ID 중복 없나?
  • not_null — 빈 값 없나?
  • relationships — 주문의 고객이 고객표에 실제로 있나? (고아 데이터 탐지)
  • accepted_values — 주문 상태가 정해진 값(delivered 등) 안에 있나?

단일(singular) 테스트

내가 직접 SQL로 짜는 맞춤 규칙. 예: "금액이 음수인 주문이 있으면 실패", "배송완료인데 결제기록이 없는 주문 찾기".

실제로 이 검사가 Olist에서 결제 누락 주문 1건을 잡아냈어요. (아래 결과 참고)

🔬 직접 확인한 것: "도미노 차단(SKIP)"

dbt는 build할 때 상위 데이터가 검사에 실패하면 그걸 쓰는 하위 모델은 아예 만들지 않습니다(SKIP). 오염된 데이터가 아래로 퍼지는 걸 막는 안전장치예요. 일부러 테스트를 깨뜨려 재현해봤습니다:

# 주문 상태 테스트를 일부러 실패하게 만들고 build
FAIL  accepted_values_stg_orders_order_status   ← 상위 실패
SKIP  fct_orders            ← 그걸 쓰는 하위는 건너뜀
SKIP  fct_daily_sales       ← 연쇄로 건너뜀
Done. PASS=7 ERROR=1 SKIP=9

7 스냅샷 — "예전엔 어떤 값이었지?" (이력 추적)

주문 상태는 시간이 지나며 바뀝니다(shipped → delivered). 보통은 덮어써져서 과거가 사라지죠. snapshot은 바뀔 때마다 과거를 보존합니다. (SCD2 기법)

실험: 한 주문의 상태를 shipped → delivered로 바꾸고 다시 snapshot을 떠봤어요. 그 주문이 2줄로 늘어납니다:

상태유효 시작 (valid_from)유효 끝 (valid_to)의미
shipped09:2109:22 (닫힘)과거 기록
delivered09:22NULL (열림)현재 값

valid_to가 비어있으면(NULL) "지금 유효한 값", 채워져 있으면 "과거 값"이에요. 이렇게 하면 "3월 시점엔 이 주문이 무슨 상태였지?"도 답할 수 있습니다.
