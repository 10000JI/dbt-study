# 1차 (워밍업) — 2026-06

## STEP 0 · 환경
- `uv venv .venv --python 3.12` + `uv pip install datafusion` → **datafusion 54.0.0** (pyarrow 24.0.0 동반).
- 이론 §2.4 "월 1회 메이저, 2026 봄 53.x" 흐름과 일치(54.0.0).
- 샘플 데이터: `data/customers.csv`(4행)·`data/orders.csv`(6행) — 조인 연습용 소형(제공된 것 역할).

## STEP 1 · SessionContext + SQL (이론 §5)
- `ctx = SessionContext()` → `ctx.register_csv("orders", ...)` → `ctx.sql("select ...").show()` 로 **등록·SQL·출력이 한 진입점**에서 됨. 이론 §5(SessionContext=진입점) 검증.
- 집계: `group by status` → completed 3건/250, shipped 2건/500, returned 1건/75.
- 조인: 국가별 매출 KR 325 · JP 300 · US 200.

## STEP 2 · EXPLAIN — 실행 파이프라인 관찰 (이론 §4) ⭐
`explain select c.country, sum(o.amount) ... join ... group by` 출력에서:
- **logical_plan**: `Aggregate → Projection → Inner Join → TableScan`
  - `TableScan: orders projection=[customer_id, amount]` → **필요한 2개 컬럼만 스캔** = **projection_push_down**(이론 §4.1) 실관찰.
- **physical_plan**:
  - `AggregateExec: mode=Partial` → `RepartitionExec: Hash([country], 8)` → `AggregateExec: mode=FinalPartitioned` = **2단계(부분→최종) 병렬 집계**.
  - `RepartitionExec partitioning=Hash(..., 8)` = **파티션 기반 병렬화**(이론 §4.2 `repartition`, §3.3) 실관찰 — 8 파티션.
  - `HashJoinExec` = 해시 조인 선택(이론 §4.2 join_selection).
  - `DataSourceExec ... file_type=csv` = 파일 스캔 노드.
- → 이론 §4 "SQL→LogicalPlan→최적화→PhysicalPlan→실행" 단계가 EXPLAIN에 그대로 보임.

## STEP 3 · SQL ↔ DataFrame API (이론 §1)
- `ctx.table("orders").aggregate([col("status")], [f.sum(col("amount")).alias("total")])` 가 SQL `group by status` 와 **같은 값**(completed 250·shipped 500·returned 75). 순서만 ORDER BY 유무 차이. → 두 API가 같은 엔진/같은 결과(이론 §1) 검증.

## STEP 4 · datafusion-cli (이론 §5 — 같은 엔진, 다른 표면)
- `brew install datafusion` → **datafusion-cli 54.0.0**(Python 패키지와 동일 버전).
- `datafusion-cli -f warmup.sql`: `CREATE EXTERNAL TABLE ... STORED AS CSV LOCATION '...' OPTIONS ('has_header' 'true')` 로 등록 → SELECT·집계·조인이 **Python과 완전히 같은 값**(KR 325·JP 300·US 200 등). → CLI/Python은 같은 엔진(이론 §1·§5).
- **관찰(차이)**: CLI의 `EXPLAIN`은 **물리계획을 ASCII 트리 다이어그램**으로 렌더(AggregateExec→RepartitionExec 8→8→AggregateExec(Partial)→HashJoinExec→RepartitionExec 1→8×2→DataSourceExec×2). Python은 logical+physical을 텍스트로. → 파이프라인 구조는 CLI 트리가 더 직관적.
- `CREATE EXTERNAL TABLE`(CLI) ↔ `register_csv`(Python)는 같은 카탈로그 등록의 다른 문법.

---

## 이론 노트 정오표 / 새로 안 것
- **`.show()` 앞에 `DataFrame()` 한 줄**: datafusion-python은 lazy — `ctx.sql(...)`는 DataFrame 객체를 만들고 `.show()`에서 실행. (repr이 먼저 찍힘)
- **EXPLAIN이 이론을 가장 잘 보여줌**: projection pushdown(스캔 컬럼 축소)·repartition(8파티션 병렬)·2단계 집계가 작은 데이터에도 다 나타남. 이론 §3.3 "벡터화·멀티스레드·파티션 병렬"이 추상이 아니라 plan에 박혀 있음.
- **register_csv vs CREATE EXTERNAL TABLE**: Python은 `register_csv`, CLI는 `CREATE EXTERNAL TABLE ... STORED AS CSV` — 같은 개념(이론 §5 TableProvider/카탈로그) 다른 표면.
- **파티션 수 = CPU 코어 수**: `RepartitionExec Hash([...], 8)`의 8은 이 Mac 논리코어 8개. `datafusion.execution.target_partitions` 기본값이 코어 수이고, `SET ...=4`로 바꾸면 EXPLAIN도 `Hash(...,4)`로 변함(실증). group 키로 해시해야 파티션별 독립 집계가 정확. 작은 데이터엔 오버킬, 대용량(2차 Olist)에서 병렬 이득.

# 2차 (본편) — Olist 실데이터 — 2026-07

> 데이터: `../dbt-poc/olist/data/olist_*_dataset.csv` (dbt 2차와 동일 데이터 재사용) · 추가: duckdb 1.5.4

## STEP 5 · Olist external table (실데이터)
- `register_csv`로 orders(99,441)·payments 등록. 상태별(delivered 96,478…)·월별 매출(2017-11 피크 ~119만) 정상.
- ⭐ **대용량 스캔 병렬 관찰**: EXPLAIN의 `DataSourceExec: file_groups={8 groups: [orders.csv:0..2206865],[..4413730],...]}` → 17MB CSV를 **8개 바이트범위로 나눠 동시 스캔**(`input_partitions=8`). 1차(6행, 1덩어리→강제 재분배)와 달리 **파일 자체가 8조각**. 이론 §3.3 파티션 병렬이 실제 이득 내는 지점. (작은 payments 5.7MB는 1덩어리 유지 — 크기 임계값)

## STEP 6 · CSV → Parquet (이론 §3.1·§6)
- `ctx.sql("select * from orders").write_parquet(...)` → **CSV 17.7MB → Parquet 6.2MB (2.8x 압축)**.
- EXPLAIN: `DataSourceExec ... file_type=parquet, projection=[order_status]` → **필요 컬럼만 스캔**(컬럼형 스토리지 projection pushdown). CSV는 전체 파싱 필요와 대조.

## STEP 7 · DataFrame API 심화 (이론 §1)
- 결제수단별 count/avg/sum을 SQL과 `ctx.table().aggregate(...).sort(...)` 두 방식으로 → **같은 값**(credit_card 76,795/1,254만·boleto 19,784/287만·voucher·debit_card·not_defined). SQL은 `round()`로 표시만 다듬음, DataFrame은 full precision.

## STEP 8 · UDF (이론 §3.2 확장성)
- `pyarrow.compute`로 스칼라 UDF `pay_bucket()`(결제액 low/mid/high 분류) 정의 → `udf(fn,[float64],string,"immutable")` + `register_udf` → **SQL에서 일반 함수처럼 호출**. 결과 high 20,107/854만·mid 62,701/677만·low 21,078/69만.

## STEP 9 · DuckDB 병행 비교 (이론 §9.1) 🎯
- 같은 "월별 매출(orders⨝payments)" 쿼리 두 엔진 실행:
  - DataFusion 25행 184ms / DuckDB 25행 310ms (참고용, 첫 실행 준비비용 포함)
  - **결과 완전 일치**: 2016-09=252.24, 2016-10=59090.48, 2016-12=19.62.
- **SQL 방언 차이 발견**: DuckDB는 `month`가 예약어라 컬럼 별칭으로 못 씀(파서 에러) → `mth`로 회피. DataFusion은 `month` 별칭 허용. 같은 SQL이라도 엔진마다 예약어/문법 미묘하게 다름.
- **API 사용감**: DataFusion=`register_csv` 후 `ctx.sql()` / DuckDB=파일 경로를 `FROM '...'`에 직접.

## 2차 정오표 / 새로 안 것
- **대용량에서 파티션 병렬이 "스캔"부터 시작**: 큰 파일은 DataSourceExec가 바이트범위 file_groups로 쪼개 병렬 읽기. 1차의 "파티션=코어수" 발견이 실데이터에선 스캔 병렬로 이어짐.
- **Parquet의 진짜 이점은 컬럼 스캔**: 압축(2.8x)도 있지만, 쿼리가 쓰는 컬럼만 디스크에서 읽는 게 핵심(projection이 스토리지까지 내려감).
- **엔진 비교 = 결과는 같고 방언·사용감이 다르다**: 정합성은 동일, 차이는 예약어·API 표면·성능 특성.
